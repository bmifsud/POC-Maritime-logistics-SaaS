# Android Chrome maritime QA demonstration

This is a deterministic local demonstration of maritime booking resilience. Android Chrome controls the demo dashboard through an SSH local-forward; Playwright and Chromium execute on Linux. GitHub Actions is not required.

## Start on Linux

```bash
cd /home/b/POC-Maritime-logistics-SaaS/frontend
npm ci
npx playwright install chromium
npm run demo:controller
```

In a second terminal, the controller is available only at `127.0.0.1:4400`. A separate preflight should be run before the interview:

```bash
curl -fsS http://127.0.0.1:4400/health
npm run test:maritime:demo
```

The test harness itself starts on port `4300` automatically. Reports are generated under ignored `frontend/artifacts/maritime-report/`.

## Android SSH tunnel

Use an Android SSH client with verified host keys and key authentication. Forward only loopback services:

```bash
ssh -N -T -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -L 127.0.0.1:14400:127.0.0.1:4400 \
  user@verified-linux-host
```

Open `http://127.0.0.1:14400` in Android Chrome. Chrome cannot create SSH tunnels itself. Keep Android and Linux online; the Playwright context alone is set offline during the test.

## Demonstration flow

1. Open the dashboard and confirm the Linux health state.
2. Tap **Run maritime demo** once.
3. Watch the fixed command run the offline-to-online sync and deterministic provider test.
4. Open the latest HTML report.
5. Show the local ADLC evidence generated by the verification gate.

The controller accepts no arbitrary command, path, or environment input. It allows one run at a time and returns the run status by polling. The dashboard survives refresh because the run state is server-owned.

## Reliability boundaries

- The reference harness is local and does not call a real booking provider.
- Provider responses are deterministic route fulfillments.
- Satellite latency is a 650 ms delay before `route.continue()` on the sync endpoint; it is not a full bandwidth or packet-loss simulation.
- Time is fixed at `2026-11-07T23:30:00.000Z`; Auckland renders the next local date.
- The Android browser and Playwright browser have separate storage; Android controls the run but does not share the Playwright context.
- Reports and auth state are ignored and must not be committed.
- For a live failure, use the generated trace. Keep a clearly labeled recording/report fallback available.

## Shutdown and cleanup

Stop the controller with `Ctrl-C`, close the SSH forwarding session, and remove ignored `frontend/test-results/` and `frontend/artifacts/` after preserving only sanitized evidence. Never copy private keys, cookies, or storage state into the repository.

## Validated status and known boundaries

Local verification completed: 43 backend tests; 6 existing portal browser tests; 15 maritime executions (5 repetitions, 3 workers); controller origin/session/path-containment test; mobile-emulated Chromium dashboard run, report-link generation and refresh recovery. This is not physical Android certification.

The actual host is ARM64 with restricted system access. Chromium required local `libnspr4`/`libnss3` extraction under `/home/b/.local/maritime-libs`; commands here used `LD_LIBRARY_PATH=/home/b/.local/maritime-libs/usr/lib/aarch64-linux-gnu`. On a normal supported Linux host use `npx playwright install --with-deps chromium` instead. The observed host has produced a Node/libuv assertion during one long-lived controller invocation; use a supported Linux host for the interview and rehearse there. No zero-flakiness guarantee is made.

The main test deliberately uses the visible **Retry synchronization** action after reconnect. Chromium on this host reports `navigator.onLine=false` even with working HTTP; the application therefore does not use that hint to block explicit synchronization. Automatic online-event recovery is separate from this verified manual-recovery path.

### Reports, retention and evidence

Reports live at repository `artifacts/maritime-report/` for direct runs, and `artifacts/demo-runs/<run-id>/` for dashboard runs. Dashboard report links identify the completed run, not a shared stale report. Reset does not delete reports. Delete old run directories manually only while the controller is stopped; startup retention removes UUID run directories older than seven days while preserving the latest recorded run. Traces may contain synthetic session cookies: keep artifacts private and do not publish them without review.

The controller is loopback-only, rejects non-loopback Host values, validates same-origin POSTs and a one-hour HttpOnly session plus CSRF token, accepts only a fixed command, limits output and run duration, and kills child process groups on shutdown. This is not a substitute for an independently reviewed production remote-execution service.

Physical Android smoke testing, actual SSH forwarding, Docker execution, fallback video preparation, and interview-host power/network validation remain operator acceptance checks. The ADLC task deliberately includes `android-chrome-smoke` with no automatic passing record.

The existing CycloneDX dependency tree reports 8 moderate npm audit findings. No forced dependency changes were made. Review these before a production release.

## Termux helper

Copy `scripts/termux-demo.sh` from this working tree to Termux private storage. It is not published to the remote repository yet. Run `bash ~/termux-demo.sh setup`, verify the server fingerprint independently, then run `bash ~/termux-demo.sh start`. The helper pins that fingerprint, uses key authentication, forwards loopback port 14400, tests health and opens the Android browser. Use `status`, `open`, and `stop` for lifecycle management. `docker-check` explicitly builds and runs on the configured SSH host after confirmation; it cannot supply a Docker daemon in unrooted Termux.

The Linux SSH endpoint must already be reachable from Android and allow forwarding to 127.0.0.1:4400. The previously tested loopback-only daemon was stopped and is not such an endpoint. Do not expose SSH publicly or disable host-key verification just to bypass this prerequisite.

## Approved branch testing

The branch-testing controller adds an authenticated branch selector populated from the fixed repository remote. Only `main` and `feat/portal-branch-testing` are approved. Runs pin the displayed full SHA, fetch into a disposable detached checkout, reject branch movement, install the selected lockfile with lifecycle scripts disabled, and invoke the fixed maritime command. Each result records branch/SHA and retains its own report. Network refresh never silently substitutes stale branch data. One active run is allowed; cold installation may take minutes.

This is trusted-branch execution, not a sandbox: tests and application code execute as the Linux account. Do not approve untrusted branches. Child test processes receive a reduced environment, but still share the account filesystem and network. Container sandboxing and physical Android acceptance remain separate gates. The existing live controller must be deliberately restarted from this version to show the selector.

Branch-runner validation: four tests passed for main and four for temp/termux-launcher in isolated fetched checkouts. Cleanup on this Android-backed host failed with EPERM/ENOSYS and a libuv abort; full lifecycle acceptance is blocked on this host. Failed cleanup is not a passing run. Validate preparation, cancellation and cleanup on a supported Linux filesystem before deployment. Mobile-emulated selector, SHA display and layout passed. The existing live single-checkout controller remains unchanged.
